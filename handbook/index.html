积木工坊 BrickForge

用户像搭积木一样拼出工厂结构；系统把车间、机器、仓库和物流映射成进程、线程、同步与调度，再据此估算产量和收益。

本页给小组查阅，不是最终需求文档。目标是先对齐：做什么、为什么能交课设、操作系统算法落在哪里、接下来一周先讨论什么。

4 人组 必须有守护进程 答辩 60%

选题一句话：可视化工厂拼装器 + 用 OS 算法驱动的产能仿真。

交互隐喻：极简几何积木。车间是大方块，机器是小方块，传送带是长条，仓库是格网。

计算承诺：布局变了、参数变了、调度策略变了，产量和收益都要跟着变。

3. 产品愿景

拼

厂区是一张平面：把车间积木拖上去，靠边会吸住，像搭乐高。点进某个车间后，平面换成该车间内部，再拖工位和机械臂。两层结构对应进程套线程。

填

点选积木后填写节拍、产能、能耗、故障率、优先级、成品单价。数据进仿真，不进空表。

算

按拓扑瓶颈、调度算法、同步等待、宕机恢复和物流路径，给出班产量、利用率、成本和收益，并可对比不同算法。

课设不是做真实 MES。我们做的是「能跑、能讲清楚 OS 原理」的教学仿真：界面像搭积木，内核像一台小操作系统在调度工厂。

5. OS 原理映射

课件后半部分给了急诊室、零售库存、网联车、快递中心四个类比。我们把它们收进同一座工厂，答辩时可以说「不是硬凑四个作业，而是一条生产链上的四类调度」。

处理机调度 → 工单调度

病人=工单，医生=机器，急诊优先级=加急订单。算法至少实现 FCFS、SJF、动态优先级、RR，并允许用户在面板切换。碎片时间对应「机器空出来但不够做下一道长工序」。

内存管理 → 库位分配

到货像进程申请内存。用首次适应 / 最佳适应把货物放进最接近需求量的货架；放不下就合并或调整分区。剩余空间记入库存碎片率，影响仓储成本。

进程同步 → 产线节拍

上下游车间要会合：没料不能开工，满仓不能下线。用信号量表示有限库位和有限夹具，用互斥保证同一工装同时只被一台机器占用。同步等待会进入产量公式。

磁盘调度 → 出货路径

订单目的地像磁道号。默认 SSTF：先送离当前发货台最近的订单，再滚雪球。可对比 FCFS 配送，展示路程差和延迟对收益的影响。

建议的 IPC 分工（不要五种都做成玩具）

机制工厂场景实现深度建议
管道相邻车间的半成品流真正用 pipe / 等价通道传批次记录，面板显示队列长度。
消息队列计划室向车间派工、质检回传结果工单结构体入队出队，可查看阻塞。
共享内存全厂看板：在制、良品、告警守护进程与 GUI 读同一块状态。

实现状态（已落地）：上表五种机制已全部实现，可在页面底部「实验台 → 同步」页一屏内看到。
  • 管道：brickforge/ipc.py 为每条「车间 → 车间」连线建一条单向管道，上游完工即投递批次，下游开工前收取。
  • 消息队列：multiprocessing.Queue 派工单、回传完工报告。
  • 共享内存：ipc.Board 用命名共享内存段做全厂看板，按「每个写入者独占一个槽位」避免读改写互相覆盖；主进程、车间进程、守护进程挂的是同一块物理内存。
  • 信号量 / 锁：库位用跨进程 Semaphore；车间内共享工装用线程信号量做互斥；共享状态用 Lock 保护。
  • 信号：brickforge/signals.py 统一封装。POSIX 上换班优先用实时信号 SIGRTMIN（可靠信号，会排队不丢失），急停用 SIGTERM，周期任务用 SIGALRM；Windows 无这些信号，降级为软信号，接口不变。

6. 守护进程（验收点）

实验评分写了「代码要跑通，守护线程有效」。课件示范的是 Linux 标准套路：fork → 父退出 → setsid → umask → chdir → 关闭 0/1/2 并重定向到 /dev/null → 业务循环。

积木工坊里，守护进程名叫 厂务精灵 Factory Daemon，职责建议收窄为三件，方便演示和答辩：

  1. 保活：监听各车间进程心跳；超时或崩溃则按策略重新拉起，并记一次「故障损失工时」。
  2. 值守配置：监视布局文件与参数文件，避免仿真进程写到一半被另一个终端覆盖（配合文件锁）。
  3. 落盘：每隔数秒把时钟、在制数量、告警写入日志文件（课件示例是每 2 秒写系统时间，我们可以写成班报）。

若主界面跑在 Windows、内核仿真跑在 WSL/Linux，守护进程放 Linux 侧更贴课件。若全栈 Web，也必须有一个独立于浏览器的后台常驻进程，不能只拿前端 setInterval 冒充 Daemon。

实现状态（已落地）：brickforge/daemon.py
  • 创建流程：POSIX 上完成课件的 7 步 —— fork 后父进程退出、setsid、umask、chdir("/")、 关闭并从 /dev/null 重定向 0/1/2，然后在独立进程里跑业务循环；另多做一次 fork，避免重新获得控制终端。Windows 无 fork/setsid，退化为「独立进程」。
  • 保活怎么做：车间进程启动时把 {pid, 车间, 作业, 信号量槽, 看板槽位} 登记进 data/procs.json，正常结束时注销自己。守护进程每 2 秒巡视：登记还在、进程却没了才算异常退出， 并按登记信息真的新建一个车间进程拉起来（同一车间最多拉 3 次，避免崩溃—重启死循环）。 所以日志里的「累计拉起」是真实的重启次数，不会把「干完活正常下班」也算进去。
  • 存活判定：Windows 上不能用 os.kill(pid, 0) 探活 —— CPython 在该平台会把它变成 TerminateProcess，也就是「检查存活」会把进程杀掉；因此改走 OpenProcess + GetExitCodeProcess。
  • 落盘：每 2 秒写 data/daemon.log 与 data/status.json，并把 pid、心跳计数、 累计拉起次数写进共享内存看板，供界面读取。写日志自带重试，抢不到文件锁不会把主循环打穿。

演示：python -m tests.test_daemon 会杀掉一个车间进程，日志里随即出现 「车间 s1 进程 pid=… 已失联，拉起新进程 pid=…」。

7. 产量与收益怎么算

初期先用可解释的公式，再视精力换成更细的事件仿真。答辩要能指着面板说「这个数字从哪条 OS 机制来」。

瓶颈产能     = min(各车间有效产能)
车间有效产能 = 机器并行能力 × (1 - 同步等待率) × 调度效率
同步等待率   = f(信号量争用, 管道阻塞, 库位不足)
调度效率     = 所选算法在当前工单集上的完成率 / 理想完成率
故障损失     = 宕机时长；有守护进程则 ≈ 检测间隔 + 拉起时间
物流延迟     = SSTF 或 FCFS 配送的总路程时间

班产量       = 瓶颈产能 × 班次时长 × 良品率
班成本       = 机器能耗 + 人工 + 库存占用 + 违约金
班收益       = 班产量 × 单价 - 班成本

让算法真正改变数字

同一套积木布局下，切换 FCFS / SJF / 动态优先级 / RR，产量、平均等待、违约次数必须不同。否则答辩时会被问「算法是不是只写在 PPT 上」。

让拼接真正改变数字

多放一台机器、打断传送带、把仓库改小，结果都要变。智能计算的「智能」首先来自结构约束，而不是空喊优化。

9. 建议系统架构

表现层

积木画布、属性面板、算法切换、产量对比图、守护进程状态灯。

仿真内核

进程/线程模型、调度器、同步原语、IPC、仓储分配、出货路径。内核不要绑死在某个 UI 库上。

厂务守护进程

独立进程。监控、拉起、写日志。与内核用套接字、消息队列或共享内存通信。

持久化

布局 JSON、参数文件、班报、锁文件。演示文件锁时用两个写入者抢同一库存账本。

数据流可以记成：画布拓扑 + 参数表 → 内核事件仿真 → 指标 → 面板。守护进程旁路监控进程表，不直接画积木。

10. 技术选型（待组会拍板）

课件示例代码是 POSIX C。内核用 C/C++ 最贴「操作系统原理」；界面用 Web 最贴「积木可视化」。两者用本地 RPC 或 WebSocket 连，是比较稳的课设形态。
方案优点风险
A. Linux C 内核 + Web 画布Daemon/IPC/文件锁都原汁原味；界面好做拼积木。要处理前后端协议，Windows 同学需 WSL。
B. 全 Python（multiprocessing + PySide/Web）开发快，进程/队列/锁都有。答辩时要主动对比 POSIX，避免被说「调用库交差」。
C. 纯前端仿真积木交互最快。守护进程和真实 IPC 很难自圆其说，不推荐作为主方案。

手册倾向方案 A。若第一周组会认为联调成本过高，可退到 B，但 Daemon 仍须独立进程。

14. 风险与待决问题

  • 可视化做太重，内核来不及：第 4 周必须先有无界面的仿真可跑。
  • 算法写了但不影响产量：对比实验要成为第 6 周演示脚本的核心。
  • Daemon 做成界面里的定时器：验收风险高，必须独立进程。
  • Windows / Linux 环境不统一：尽早定 WSL 或实验楼 308 的环境。
  • 题面像企业管理软件：材料里反复强调「OS 驱动的仿真」，不要写成进销存。
